## 这是什么

一个「把本地音乐库播到**小爱音箱**、并顺手把界面做得好看点」的小作品。

**它最先解决的是「服务器放哪」这件事：不用买 NAS，不用腾一台小主机，也不用让电脑常亮。**
一台闲置的 Android 手机或平板就够了——作者用的是**小米平板 5**（老机器，二手几百块），装个 Termux 就是服务器。
整套东西的重量是「一个 App + 两个 Python 进程」，不是「一台设备 + 一套容器编排」。
不用装 Docker，不用写 compose，不用给 NAS 插硬盘；不跑的时候它就是一台平板。

同类方案里最常见的两种形态是「NAS + Docker Compose」和「专门买台小主机/软路由」，
两者都要先解决**额外硬件**这件事；这里的起点是「你抽屉里那台不用的手机」。

它本质上是 **[xiaomusic](https://github.com/hanxi/xiaomusic)** 的一层界面与体验增强：xiaomusic 负责把音频推给音箱、控制播放，本项目负责把这件事变得能看、能找歌、能调歌词。没有 xiaomusic 和一台小爱音箱，这套代码没有可以输出的地方。

由四部分组成：

| 目录 | 内容 | 形态 |
|---|---|---|
| `web/` | 一套纯前端页面（PC 宽屏版 + 手机版） | 单个 `.html`，无构建步骤 |
| `server/` | 一个 Python 服务，负责封面、歌词、推荐、播放状态聚合 | 单文件 `server.py` |
| `pc-client/` | 桌面客户端外壳（Electron） | 加载上面那套网页 |
| `android/` | 手机端外壳（Android WebView） | 加载上面那套网页 |

**它不是一个能独立运行的产品**：页面需要连到你自己部署的后端，后端需要连到你自己的 **xiaomusic** 实例，xiaomusic 再去驱动你的 **小爱音箱**。仓库里只包含作者本人写的这部分代码，前两环都不在仓库内。

## 三个值得一提的地方

1. **服务器不用额外买。** 起手是一台抽屉里的安卓机，不是购物车里的 NAS。少一台常亮设备、少一套容器编排，
   也少一块专门给它插的硬盘——代价是 Android 会杀后台，得手动把 Termux 的电池优化关掉（这一点写在部署那节）。
2. **三端一套代码。** PC 宽屏版、手机版、Electron 桌面壳加载的是同一套页面，改一处三端同时生效；
   代价也很实在——`pc.html` 与 `remote.html` 是两份高度重复的实现，改样式要同步改两遍（下面「更好的版本」里那条合并成 PWA 的建议就是冲它去的）。
3. **边角是真调过的。** 切歌后的残影、进度与歌词的归零时机、设备上报位置属于哪一首、
   续播后 12 秒内的误判窗口……这些不写在功能列表里、但天天影响手感的地方，代码里有一堆为此写的防护。
   作者在真机上迭代了一百多轮，大部分时间花在这上面。

## 它跑在什么环境里

作者本人的实际部署（供参考，不是要求）：

```
[ 手机版网页 / PC 网页 / Electron 客户端 / Android 壳 ]
                     │  HTTP
                     ▼
        鲸屿Mic server  :58091   ← 本仓库（封面/歌词/推荐/状态聚合）
                     │  HTTP
                     ▼
          xiaomusic     :58090   ← 外部项目，独立部署
                     │  小米云 / 局域网协议
                     ▼
            小爱音箱 Play (L05B)  ← 实际出声的设备
```

- **xiaomusic**（[:58090](https://github.com/hanxi/xiaomusic)）：曲库扫描、向设备下发播放指令、DLNA、状态回读。本项目**不包含**它的代码，需要你独立部署。
- **小爱音箱**：真正的输出端。作者用的是 **小爱音箱 Play（型号 L05B）**；理论上 xiaomusic 支持的其他小爱型号也能用，但**作者只在 L05B 上验证过**，其他型号的差异（音量粒度、`loop_type` 行为、播放状态字段）可能让状态机判断失准。
- 两者之间还有一层**小米账号登录态**。音箱显示"离线"时，绝大多数情况不是网络问题，而是登录态过期——这一点在 xiaomusic 的文档里有说明。

> 本项目与小米、小爱音箱、xiaomusic 的作者**均无隶属、合作或背书关系**。上述名称仅用于说明本程序在什么环境里工作、依赖了什么。

## 完整功能需要的软硬件

想跑出「和截图一样」的完整体验，需要下面这些。**打 ★ 的是缺了就跑不起来的**。

### 硬件

| 项 | 说明 | 参考 |
|---|---|---|
| ★ 一台能常开的 Linux 环境 | 跑 xiaomusic + 本项目的 server。**最省事的一条：一台闲置安卓手机/平板 + Termux**，不用额外买硬件；软路由 / NAS / 旧笔记本 / 树莓派 / 迷你主机也都能跑 | 作者用的是**小米平板 5 + Termux + proot-distro (Debian)**，成本最低；缺点是 Android 会杀后台，需要关电池优化 |
| ★ 小爱音箱 | 至少一台，需与主机处于**同一局域网**，且能通过小米账号被控制 | 小爱音箱 Play（L05B） |
| ★ 局域网 | 主机、手机、PC、音箱互通；跨网段/开了 AP 隔离会导致设备"看得见控不动" | 普通家用路由器即可 |
| ○ 电视 / 支持 DLNA 的音箱 | 仅「切换输出设备」功能需要 | 小米电视 S55 之类支持 DLNA 的机型 |

> **关于 root：不需要。** proot 容器里的 `/root` 是「假 root」，落到宿主机上就是 Termux 的普通应用身份
> （`u0_aNNN`）。服务、静态页、曲库都以这个身份读写，全程没有提权。
> 网上说的「平板部署必须 root」，多半是因为走 `adb shell su -c ...` 去写应用私有目录——
> `adb shell` 登录的是 `shell` 用户，所以不得不 `su`；改成 `ssh` 以 Termux 用户身份直接 `cp`，
> 这一步就不存在了。**没有 root 的设备请走 ssh，不要照抄 adb + su 那套。**
> 唯一需要人工确认的是系统级设置：关掉 Termux 的电池优化、开唤醒锁、允许自启（adb 能改一部分，但通常要手动点）。

## 部署：可以直接交给 AI

这套东西的部署流程比较绕（跨主机、两个服务、端口转发、设备登录态），但**每一步都是确定性的、有明确判据的**——所以**完全可以直接把仓库丢给一个 AI 编程助手，让它照着部署**。

作者本人就是这么迭代的。如果你打算这么做，把下面这段话连同仓库一起给 AI：

> 这是一个依赖 xiaomusic 与小爱音箱的前端 + 聚合服务项目。请帮我：
> 1. 在这台机器上部署 `server/server.py`，监听 58091，并让它指向本地 `:58090` 的 xiaomusic；
> 2. 确认 xiaomusic 已能控制我的小爱音箱（用 `/getplayerstatus` 验证，`status:1` 出声、`2` 暂停、`0` 停止）；
> 3. 把 `web/` 目录挂到 xiaomusic 的静态目录下，或单独起一个静态服务器；
> 4. 打开 `web/pc.html`，在设置里填服务地址与设备 ID，验证搜索、播放、进度、歌词四件事。
>
> 注意：仓库是 as-is 分享，代码里可能有针对原作者环境的硬编码（端口号、设备 ID、路径），请你按我的实际环境改写，不要照抄。

需要提醒 AI 的几个坑（作者踩过的，已写进代码注释）：

- **端口分工固定**：`:58090` 是 xiaomusic（接受相对路径），`:58091` 是本项目（**必须带 `MM + "/api/..."` 前缀**，否则 404）。
- **判断设备是否真在响，只看 `/getplayerstatus`**，不要相信软件层的 `is_playing` 标志。
- **音量不要信回读值**，必须 POST `/setvolume` 下发，再重新读一次确认。
- **安卓壳在后台容易被杀**，主机若是手机/平板方案，记得关掉电池优化。
- **主机若是安卓机，定期重启是运维动作不是可选项**：内核不可回收内存会随时间累积（实测约 230 MB/天），
  攒到几个 GB 之后清后台杀应用都没用，系统靠 ZRAM 换页硬撑，整机卡到不能看。**每 3~5 天重启一次**。
  重启本身不难，难的是**重启后服务得自己回来** —— 系统会拦掉 `Termux:Boot` 且不报错，
  得用 Magisk `service.d` 兜。两个坑和现成脚本见 [`deploy/`](deploy/)。

### 但有些事 AI 替你做不了

把边界说清楚，省得白等：

| 只能人来做的 | 为什么 |
|---|---|
| 小米账号登录 | 扫码 / 短信验证码必须你本人收，AI 拿不到 |
| 音箱绑定到账号、取设备 DID | 同样是账号侧操作 |
| 音箱配网、确认在同一局域网 | 手机 App 里点的 |
| 关电池优化 / 开唤醒锁 / 允许自启 | 系统设置 UI，部分机型 adb 也改不了（**已 root 的话可自动化，见 [`deploy/`](deploy/)**） |
| `su` 授权弹窗（如果走 adb 路径） | 弹窗要人点 |
| **听感判断**：切歌有没有残影、播完会不会复播、歌词快慢 | 只能耳朵听，日志看不出来 |

**能复刻到什么程度**，取决于两件事：

1. **音箱型号**。作者只在小爱音箱 Play（L05B）上验证过。换型号后 `loop_type`、音量粒度、
   状态字段可能不一样，状态机（防误切、防复播、进度归属）的判断会失准，需要重新调。
   想要一模一样的效果，**最好同型号**。
2. **代码要不要改**。用仓库里这份原文不改，坑已经修在代码里了；一旦你为了适配环境去改端口/路径/设备逻辑，
   就得自己重新跑一轮真机验证——作者那 100 多轮就是这么来的。

一句话：**AI 能把「跑起来」做到接近满分，"手感"要到场听。**

## 功能

- 曲库浏览、搜索、队列、播放控制（网页 + 桌面 + 手机三端同源）
- 每日推荐：按标签挑歌、主题歌单、多路信号排序，支持「加载更多」
- 歌词：解析、双语配对、逐行时间微调、缺失时自动补
- 播放状态机：切歌不留残影、进度/歌词归零、播完不原地重播
- 桌面歌词窗口、音量与输出设备切换（DLNA）
- 明暗两套配色，PC 两栏布局、手机单手布局

## 构建

**不提供构建支持。** 下面只是说明现状，不构成帮助承诺：

- `web/` 与 `pc-client/` 是纯静态 + Electron，没有打包流程需要学习
- **PC 客户端**：`cd pc-client && npm install && npm start` 即可跑。
  - 打 Windows 安装包：`npm run build:win`。`package.json` 里已写好完整的 `build` 段
    （electron-builder，NSIS x64，产物在 `dist/鲸屿Mic-PC-Setup-<version>.exe`）。
    `build.electronDist` 指向 `node_modules/electron/dist`，省掉一次 158 MB 的重复下载；
    若 `npm i` 的 postinstall 被跳过导致该目录不存在，手动解 `electron-v<ver>-win32-x64.zip` 进去即可。
  - 只想要免安装的便携版，仍可用
    `npx @electron/packager . JingYuMic-PC --platform=win32 --arch=x64 --icon=icon.ico`。
  - `electron` 在 `devDependencies` 里，不会被打进 `app.asar`（`build.files` 是白名单）。
  - ⚠️ `electron` 的版本请保持**精确值** `45.0.0`。写成 `^45.0.0` 会解析到 45.2.x，
    与 release 包里那个运行时不一致。
- `android/build.sh` 是作者自用的脚本，依赖本机 SDK 路径；脚本会在缺证书时自动生成一个**调试用**证书，正式发布请换成你自己的
- `server/server.py` 直接 `python3 server.py` 运行，无第三方依赖清单

## 如果你想要更好的版本

作者不会继续投入，但下面几条是明确的改进方向，Fork 之后值得先做：

**结构性（收益最大）**

1. **从协议层根治"播完复播"**。作者的处理是"在设备硬件循环绕回之前抢先把下一首推上去"，
   属于时序竞态——用结尾淡出检测 + 预提前量把它压到几乎不发生，但没有消除可能
   （**这套逻辑落在 xiaomusic 一侧的播放器里，本仓库不含那部分补丁**；仓库里只有前端状态机这一层防护）。
   真正的解法是在向设备下发播放时把 `loop_type` 显式置为 `0`（单曲不循环），让设备自己不再绕回。
   作者没找到可靠的写入点（xiaomusic 的 `_play` 只推一个 URL，从不设置该字段），所以留了这个口子。
2. **用 Docker / systemd 取代"平板 + Termux"**。作者选平板是因为手边有闲置设备，代价是 Android 会杀后台、proot 有性能损耗、重启后要手动拉服务。任何一台 x86 小主机 + Docker Compose 都更稳。
3. **三端页面合并成一个 PWA**。现在 `pc.html` 与 `remote.html` 是两份高度重复的代码，改一处要同步两处，这是本项目最大的维护负担。合并成单一响应式页面 + Service Worker 可以砍掉一半代码量。

**体验性**

4. **推荐算法换成向量检索**。现在是标签 + 多路信号加权排序，冷启动和长尾都不太好；本地曲库规模不大时，用一个小嵌入模型做相似度会明显更准。
5. **歌词时间轴自动对齐**。现在缺时间轴时靠估算，误差几百毫秒；接一个强制对齐（forced alignment）模型可以做到逐字。
6. **把设备状态轮询换成事件推送**。现在是前端定时问 `/playingmusic`，多端同时开着会有冗余请求。

**更省事的替代方案**

如果你只是想要"手机上控制小爱音箱放自己曲库"，不想折腾部署：

- 直接用 **xiaomusic 自带 Web 界面**，功能覆盖了播放和曲库，只是 UI 比较朴素；
- 用 **Music Assistant**（Home Assistant 生态）做统一音乐中枢，原生支持多种音箱协议，界面和推荐都更成熟；
- 只是想听歌、不需要本地曲库的话，主流音乐 App + 智能音箱绑定是成本最低的路。

本项目的价值主要在于**界面细节和播放状态机的打磨**（切歌残影、进度归零、歌词对齐这些琐碎但影响体感的地方），如果你不在意这些，用上面任一方案都更省事。
